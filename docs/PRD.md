# Indie Payment Kit PRD

- 产品状态：v0.1 开源首版
- 项目归属：BeatAPI
- 目标仓库：`BeatAPI/indie-payment-kit`
- 核心形态：一个用户入口 Skill + 可选 Codex Plugin 包装

## 1. 产品定义

Indie Payment Kit 是面向独立开发者的统一支付接入入口。开发者只需安装
一个 Skill，项目即可完成支付相关的项目扫描、路线选择、支付商推荐、官方
Skill/MCP 交接以及统一上线验收。

它不代替 Stripe、Dodo、支付宝或微信支付的官方实现，也不成为新的聚合支付
网关。它负责压缩开发者在八套文档、八种安装方式和多套支付生命周期之间的
认知与操作成本。

一句话定位：

> 一个 Skill，选对支付、接通支付、验证到可以上线。

## 2. 商业目标

这是 BeatAPI 的开发者获客型开源项目，第一目标不是直接收费，而是建立以下
开发者资产：

1. 让正在解决支付问题的开发者认识 BeatAPI；
2. 通过真实工具价值建立技术信任，而不是单纯投放品牌内容；
3. 将 GitHub、Skill 市场和搜索流量承接到 BeatAPI 开发者生态；
4. 验证“一个入口完成选型、官方能力编排与验收”能否扩展到 Auth、Email、
   Storage 和 Deploy 套装。

开源安装量本身不等于拥有用户。项目必须通过 GitHub Discussions、更新订阅、
开发者社区和 BeatAPI 模板入口形成透明、可选的后续关系。

## 3. 目标用户

### 首要用户

- 正在开发 SaaS、AI 工具、API 或数字产品；
- 使用 Codex、Claude Code、Cursor 等 coding agent；
- 没有专职支付工程师；
- 在产品即将收费、迁移支付商或准备上线时遇到阻力；
- 需要在中国大陆和全球支付路线之间做选择。

### 暂不服务

- 有成熟支付团队的大型企业；
- 寻找资金归集、二清或资质绕过方案的商户；
- 只需要线下 POS、复杂收单硬件或银行级清结算的项目；
- 希望 Agent 未经确认直接操作生产账户或真实资金的用户。

## 4. 用户问题

开发者当前需要分别完成：

```text
搜索支付商 -> 阅读多家官方文档 -> 安装多套 Skill/MCP
-> 判断主体与市场资格 -> 选择支付商 -> 接代码
-> 处理 Webhook/退款/订阅/权益 -> 验证上线
```

主要成本不是单个 API 调用，而是：

- 不知道应该选直连支付还是 Merchant of Record；
- 不知道个人、国内公司、海外公司分别能走什么路线；
- 官方 Skill 只解释自己，不负责跨支付商比较；
- 生成 checkout 容易，但重复 Webhook、退款撤权和订阅状态很容易出错；
- “代码写完”“沙箱通过”“生产可收款”经常被错误地合并成一个状态。

## 5. 核心价值

### 对开发者

- 一个安装入口；
- 一个项目扫描结果；
- 一份主推荐与真实备选；
- 只加载被选中支付商的官方能力；
- 一套跨支付商生命周期和上线验收；
- 明确知道当前完成到了哪一层。

### 对 BeatAPI

- 以高频、高痛点的开发任务获取精准开发者；
- 形成可以被搜索、收藏、安装和贡献的开源资产；
- 将 BeatAPI 从“AI 视频 API”扩展为可信的独立开发者工具品牌；
- 为后续 Indie Launch Kit 系列验证统一产品协议。

## 6. v0.1 范围

### 覆盖支付商

| 路线 | 支付商 | v0.1 能力 |
|---|---|---|
| 全球直连 | Stripe、PayPal | 选型 + 官方交接 + 通用验收 |
| Merchant of Record | Dodo、Paddle、Polar、Creem | 选型 + 官方交接 + 通用验收 |
| 中国大陆 | 支付宝、微信支付 | 选型 + 官方交接 + 通用验收 |

### P0 功能

1. 一个可被 Agent 自动发现的 `indie-payment-kit` Skill；
2. 扫描 JavaScript/TypeScript 项目的框架和支付 SDK 信号；
3. 基于市场、主体、产品、计费、税务偏好和技术栈生成确定性推荐；
4. 双市场项目输出全球和中国大陆两条路线；
5. 八家支付商的官方 Skill/MCP/文档交接适配器；
6. 统一支付生命周期契约；
7. 上线验收清单与六级证据状态；
8. 无遥测、无密钥收集、推荐规则公开；
9. 自动测试、仓库校验和 GitHub Actions。

### P1 功能

- Stripe、Dodo、支付宝、微信支付的框架级引导接入；
- 针对 Next.js、TanStack Start、Hono 的差异化适配；
- 自动生成支付接入计划和验收报告文件；
- Provider Skill 来源自动更新和变更提醒；
- 可重复运行的沙箱 Webhook、幂等、退款和撤权测试夹具。

### 非目标

- 不托管 MCP 或用户支付凭证；
- 不代理商户开户、KYB、结算或资金流；
- 不把八家 SDK 一次性安装进项目；
- 不复制八家官方 Skill 全文；
- 不承诺一键完成生产审核；
- 不以商业合作暗中影响推荐排序。

## 7. 用户流程

```text
安装 Skill
  -> 扫描项目
  -> 补充缺失的六项输入
  -> 输出主推荐和备选
  -> 用户确认
  -> 只加载目标 Provider Adapter
  -> 调用当前官方 Skill/MCP/SDK
  -> 按统一生命周期实现或检查
  -> 执行上线验收
  -> 输出证据等级和剩余阻塞项
```

生产账户创建、产品创建、退款、订阅变更和其他外部写操作必须在执行前获得用户
明确授权。

## 8. 关键产品规则

1. 先选择路线，再选择具体支付商；
2. 不把直连支付与 MoR 当作同一商品进行简单费率比较；
3. 支付成功以验签 Webhook 或服务端查询为准；
4. 浏览器成功页不能直接开通权益；
5. 订单、订阅和权益属于产品域，不属于 Provider SDK；
6. 推荐只能表达适配度，不能表达开户资格已获批准；
7. 支付商资料超过 180 天未核验时，仓库校验失败；
8. 所有支持状态必须使用统一等级，不得把“有文档”写成“生产可用”。

## 9. 成功指标

### 获客漏斗

- GitHub 仓库访问与 Star；
- Skill 安装量；
- 项目扫描完成数；
- 推荐结果生成数；
- 官方支付商接入继续执行数；
- 进入 BeatAPI 文档、模板和开发者社区的自愿转化数。

### 核心价值指标

- 首笔沙箱支付验证完成率；
- 从安装到首笔沙箱支付的中位时间；
- 验收工具发现的真实支付生命周期问题数；
- 第二个项目或第二个支付通道的重复使用率；
- 外部贡献的 Provider 更新和适配器 PR 数量。

### v0.1 验证门槛

- 10–15 个外部独立开发者项目参加测试；
- 至少 5 个项目完成首笔沙箱支付；
- 至少 3 个项目完成重复 Webhook 和退款/取消权益检查；
- 至少 2 个开发者将工具用于第二个项目、迁移或第二支付通道。

如果用户只收藏对比表而不运行扫描和验收，应将它判断为内容获客资产，而不是
已经验证的工具型需求。

## 10. 风险与缓解

| 风险 | 缓解 |
|---|---|
| 官方 Skill 快速迭代导致资料过期 | 只保留路由与来源，设置核验日期和 CI 时效门槛 |
| 八家覆盖导致维护失控 | v0.1 深度能力分级，按需加载，不承诺同等成熟度 |
| 推荐被认为带有商业偏见 | 公开规则、公开数据、披露合作，不默认遥测 |
| 用户误以为可以绕过支付资质 | 明确区分适配度、开户资格和生产验证 |
| Agent 操作真实资金 | 沙箱优先，所有生产外部写操作执行前确认 |
| 安装量无法沉淀为用户 | 建立自愿的 GitHub、社区和更新订阅承接 |

## 11. 后续产品线

支付获得真实使用证据后，再复用同一协议扩展：

```text
scan -> choose -> official handoff -> implement -> verify
```

候选套装：Auth、Email、Storage、Analytics、Deploy。它们共享品牌与安装体验，
但保持独立 Skill，避免一个总 Skill 变成无法维护的通用知识库。
